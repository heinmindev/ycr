### 0.1 What F-002 is

**FACT — ADR-0020 §Decision items 2–3 and §Follow-up work:** F-001 shipped the authorization pipeline with **no authentication handler in `src/`**. ADR-0016's token and refresh implementation was deferred to "a dedicated follow-up feature". F-002 is that feature.

**FACT — `TASKS.md` T-023 Notes (hein, 2026-09-23):** today no endpoint can be called outside the test suite. Every station route answers `401` in a running instance, which was confirmed while checking T-021's Scalar UI.

**FACT — ADR-0020 §Consequences:** "Until the follow-up feature lands, the system cannot authenticate a real user, so F-001 is not independently deployable."

**FACT — `docs/10` §Station permission grants and ADR-0020 decision item 7:** "No grant is seeded in application code. No identity/role provisioning system exists yet". Role→permission provisioning therefore arrives with F-002.

**ENGINEERING DECISION (tech lead, cite ADR-0005):** backend only. No SPA exists (OQ22). Consequences for the SPA-side controls are in D16.

## 4. Scenarios (Given / When / Then)

"Matching `Origin`" means the request's `Origin` equals a configured allowed origin (R9). Timestamps are driven by a fake `TimeProvider`. Unless a scenario says otherwise, a user created for it has already changed their must-change password (R26), and rate limits are set high enough not to interfere (S5 and S12 test them).

### Login

- **S1.** Given an active user with valid credentials and a matching `Origin`, when they POST `/api/v1/auth/login`, then the response is `200` with `{ accessToken, expiresAtUtc }` where `expiresAtUtc` is 15 minutes after issue. `Set-Cookie` carries the refresh token with `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth/refresh`. One `identity.AuthSessions` row exists with `RevokedAtUtc` null and `ExpiresAtUtc` 12 hours after creation, and the stored refresh-token value is a **hash**, never the raw token (R5; S31). One `Identity.LoginSucceeded` audit row is written (R22). The user's failed-attempt count is reset to 0.
- **S2. Uniform rejection.** Each of: wrong password for an active user; an unknown username; a disabled user with the **correct** password; a locked user with the **correct** password → `401` ProblemDetails `Auth.InvalidCredentials`. The four responses are identical apart from `traceId`, none has `Set-Cookie`, and no session is created (R23). Equalised timing: the unknown-username path performs a full password-hash verification, asserted by the test, not by measuring wall-clock time.
- **S3. Disabled user.** A disabled user with the correct password → as S2; one `Identity.LoginFailed` audit row whose subject is that user. The failed-attempt count is not the mechanism that rejects them; disablement is.
- **S4. Lockout.** Nine consecutive failures, then a success → `200`, count reset. Ten consecutive failures → the tenth writes `Identity.LoginFailed` and `Identity.LockedOut`; for the next 15 minutes the correct password → `401 Auth.InvalidCredentials` (S2) and one `Identity.LoginFailed`; after 15 minutes the correct password → `200`. An unknown username never locks anything and writes `Identity.LoginFailed` with a null `SubjectId` and no typed value (R22). **Administrator unlock (U3):** while the user is locked, a `SystemAdministrator` POSTs `/users/{id}/unlock` → `204`, the lockout end and the failed-attempt count are cleared, one `Identity.UserUnlocked` audit row is written, and the correct password → `200` at once. A caller without `users.manage` → `403`; an unknown id → `404 Identity.UserNotFound`.
- **S5. Rate limit.** With a test-configured limit, login attempts over the limit **for one username** (from varied client addresses) → `429` ProblemDetails `Auth.TooManyRequests`; attempts over the limit **from one client address** (for varied usernames) → the same. A rejected-by-limit request evaluates no credentials, writes no audit row and does not count towards lockout. Limits come from configuration (R16). **Defaults (U6):** with no override, the 6th login within a minute for one username → `429`, and the 21st login within a minute from one client address → `429`; a test asserts these are the shipped defaults.
- **S6. Origin on login.** Login with a missing `Origin`, or one not matching → `403` ProblemDetails `Auth.OriginRejected`; no credentials evaluated, no audit row, no failure count increment, no `Set-Cookie` (R9).

### Refresh and rotation (ADR-0016 §Required tests)

- **S7.** Valid refresh cookie + matching `Origin` → `200` with a new access token. The presented token gets `RotatedAtUtc` and `ReplacedByTokenId`, the new cookie replaces it, and the session's `ExpiresAtUtc` is unchanged (absolute lifetime, no idle extension). No audit row (not in R22).
- **S8. Two-tab race.** Two concurrent refreshes with the same token → exactly one `200` with rotation. The other gets `409 Auth.RefreshSuperseded` with **no** tokens, and the family is **not** revoked. A retry with the successor cookie succeeds.
- **S9. Predecessor inside grace.** The immediate predecessor presented within the grace window (default 20 s) → `409 Auth.RefreshSuperseded`, no `Set-Cookie`, no access token, family intact; an `AuthRefreshSuperseded` log/metric event and **no audit row** (R7).
- **S10. Predecessor outside grace.** The same presentation after the window → the session's `RevokedAtUtc` is set (reason `FamilyReuse`), `401 Auth.RefreshInvalid`, and exactly one `Identity.RefreshFamilyRevoked` audit row (R8). A subsequent refresh with the successor also fails `401 Auth.RefreshInvalid`, and the session's access tokens are rejected within ≤30 s.
- **S11. Ancestor reuse.** An older ancestor, at any time → as S10.
- **S12. Origin and limits on refresh.** Missing `Origin` → `403 Auth.OriginRejected`; wrong `Origin` likewise; no rotation, no tokens (R9; `docs/18:34`). Refreshes over the test-configured per-address limit → `429 Auth.TooManyRequests`, no rotation (R16); with no override the 31st refresh within a minute from one client address → `429` (U6 default).
- **S13. Lifetimes.** A refresh presented after the session's 12-hour absolute lifetime → `401 Auth.RefreshInvalid`, no rotation. An access token past its 15-minute `exp` → `401 Auth.Unauthenticated`. An unexpired access token whose session has passed its absolute lifetime → `401 Auth.Unauthenticated` (the session is no longer active, R2).
- **S14.** Refresh on a revoked session, with a missing cookie, or with an unknown token → `401 Auth.RefreshInvalid`, no tokens.

### Logout, password change, disablement, revocation (ADR-0016 §Required tests)

- **S15. Logout.** An authenticated user POSTs `/auth/logout` with a bearer token and matching `Origin` → `204`. The session named by the token's `sid` gets `RevokedAtUtc` (reason `Logout`); the response carries a `Set-Cookie` that expires the refresh cookie with `Path=/api/v1/auth/refresh`; one `Identity.LoggedOut` audit row. The next refresh with the old cookie → `401 Auth.RefreshInvalid`, and a request with the old access token → `401` within **≤30 s** (R3). The user's other sessions are untouched. Missing `Origin` → `403 Auth.OriginRejected`, nothing revoked. No bearer token → `401 Auth.Unauthenticated`.
- **S16. Password change.** A user with sessions A (current) and B POSTs `/auth/password` from A with the correct current password and a new password of 12–128 characters not on the blocklist → `204`; B is revoked (reason `PasswordChanged`) and its access token is rejected within ≤30 s and its refresh fails; **A stays active**; one `Identity.PasswordChanged` audit row. A new password of 11 or 129 characters, or on the blocklist, → `400 Auth.PasswordRejected`, nothing changed; a wrong current password → `422 Auth.CurrentPasswordIncorrect`, nothing changed (U1: `/auth/*` → `Auth.*`). If the user had a must-change password, the flag is cleared (R26).
- **S17. Disabled user.** A `SystemAdministrator` POSTs `/users/{id}/disable` for a user with two live sessions → `204`; both sessions revoked (reason `UserDisabled`), their access tokens rejected within ≤30 s and their refresh fails; one `Identity.UserDisabled` audit row; login then → S2's uniform `401`. `/users/{id}/enable` → `204`, one `Identity.UserEnabled`, login succeeds. A `SystemAdministrator` disabling **their own** account → `422 Identity.CannotDisableOwnAccount`, nothing changed, no audit row (U5; see S19e for the last administrator).
- **S18. Removed permission within 30 s.** A user whose only role is `StationManager` (so holds only `stations.read`) calls `GET /api/v1/stations` → `200`. A `SystemAdministrator` replaces their roles with `[]` via `PUT /users/{id}/roles` → within ≤30 s the same call returns `403`, with no re-login; one `Identity.RolesChanged` audit row with before `["StationManager"]` and after `[]`. The same bound holds when a `RolePermissions` row is removed directly in the store (grants change by migration, R11).
- **S19. Session revocation.** A `SystemAdministrator` POSTs `/auth-sessions/{id}/revoke` → `204`; that session's `RevokedAtUtc` is set (reason `AdministratorRevoked`), its access token is rejected within ≤30 s and its refresh fails; one `Identity.SessionRevoked` audit row. The user's other sessions are untouched. A caller without `auth-sessions.revoke` → `403`.
- **S19a. Administrator password reset.** A `SystemAdministrator` POSTs `/users/{id}/password-reset` → all the user's sessions are revoked (reason `AdministratorPasswordReset`); one `Identity.PasswordReset` audit row; the old password no longer signs in; the new password signs in and is must-change (R26, S19d). A new password rejected by the D2 policy → `400 Identity.PasswordRejected` (U1: `/users/*` → `Identity.*`). A `SystemAdministrator` resetting **their own** password here → `422 Identity.CannotResetOwnPassword`, nothing changed (U5: they use `POST /auth/password`).
- **S19b. Own roles.** A `SystemAdministrator` PUTs `/users/{their own id}/roles` with any value → `422 Identity.CannotChangeOwnRoles`; roles unchanged; no audit row (R20).
- **S19c. Unlock.** As in S4's administrator-unlock case (U3). Unlocking a user who is not locked → `204`, nothing changed, no audit row.
- **S19d. Must-change password (U2, R26).** A user whose password was set by an administrator (create or reset), or the bootstrap administrator, signs in → `200` with tokens. With that session: `GET /auth/me` → `200`; `POST /auth/refresh` → `200`; `POST /auth/logout` → `204`; every other authenticated endpoint — for example `GET /api/v1/stations` and, for a `SystemAdministrator`, `GET /users` — → `403 Auth.PasswordChangeRequired`, even though the user holds the permission. After `POST /auth/password` succeeds, the same calls succeed without a new sign-in.
- **S19e. Last administrator (U5, R27).** With exactly one active `SystemAdministrator` A and another `SystemAdministrator` B who is disabled: enabling and then disabling B is allowed while A remains; removing `SystemAdministrator` from A, or disabling A, by any path that reaches the check → `422 Identity.LastAdministrator`, nothing changed, no audit row. Through the API these operations are normally stopped first by the self-target rules (S17, S19a, S19b), so the check is also exercised at application level. **Concurrency:** two active `SystemAdministrator`s who each disable the other at the same moment → exactly one succeeds and the other gets `422 Identity.LastAdministrator`; at least one active `SystemAdministrator` always remains.

### Access tokens and the pipeline

- **S20.** A decoded access token has header `alg` = `ES256` and a `kid`, and payload claims exactly `sub`, `sid`, `iss`, `aud`, `exp`, `iat`, `nbf`, `jti` — no other claim (R1).
- **S21.** A token that is tampered with, expired, signed with the wrong key, signed with another algorithm (including `HS256` and `none`), carrying the wrong `iss` or `aud`, or whose `sid` names a revoked or unknown session → `401 Auth.Unauthenticated`.
- **S22. Challenge body (ADR-0020 follow-up, D14).** With the real scheme registered, an unauthenticated request to a protected endpoint returns `401` with `WWW-Authenticate: Bearer` and a ProblemDetails body with `errorCode` `Auth.Unauthenticated` and `traceId`. `Common.Unauthenticated` appears nowhere in `src/`. The `AuthorizationResultHandler` type no longer exists (asserted by test). `MissingSchemeTests` is rewritten to this premise.
- **S23. Startup guard.** Outside `Testing`, startup succeeds with exactly the framework `JwtBearerHandler` registered and **throws** if any other scheme is registered. Both halves are tested (ADR-0020 item 6, as amended).
- **S24. Architecture rule.** The S21a test still passes with F-002's code unchanged, and its violating fixture still fails it (D15).
- **S25. Unmodified production composition (`docs/21` §Tests).** With no `ConfigureTestServices` overrides: the first administrator is created by the bootstrap path (D10), their password is changed through `/auth/password`, they log in, and `GET /api/v1/stations` with the issued token → `200`; the same call anonymously → `401 Auth.Unauthenticated`. Real tokens throughout (D13).
- **S26. Wrong permission.** An authenticated real user whose only role is `TicketOperator` POSTs `/stations` → `403`; the same user calling any §6.2 endpoint → `403` (`docs/21` §Tests).
- **S26a. Signing key.** Production startup with a signing key marked development-only, or matching a known development key, fails (R14).

### Browser controls

- **S26b. No CORS.** A preflight `OPTIONS` request from a foreign `Origin` receives no `Access-Control-Allow-*` header, and no endpoint response carries one (R24).
- **S26c. Security headers.** Every API response, including ProblemDetails errors, carries `X-Content-Type-Options: nosniff`, a restrictive `Content-Security-Policy` including `frame-ancestors 'none'`, and a `Referrer-Policy` (R24). Exact header values are fixed in PLAN.

### Audit and secrets

- **S27.** Every `Identity.*` audit event written by an administration endpoint has `ActorUserId`, `ActorRole` (canonical identifiers) and `AuthorizedByPermission` from the server-side context only; a request body or header naming another user or role cannot influence them (R12; F-001 S20 pattern). **Events with no bearer principal (U4):** `Identity.LoginSucceeded` → `ActorUserId` is the user who signed in and `ActorRole` their roles; `Identity.LoginFailed` and `Identity.LockedOut` → `ActorUserId` and `ActorRole` null, `SubjectId` the resolved user (null if none); `Identity.RefreshFamilyRevoked` → `ActorUserId` and `ActorRole` null, subject the session's user. A login request whose body or headers name another user cannot change any of these.
- **S28.** After exercising S1–S21, no captured log line, no audit row and no ProblemDetails body contains a password, a password hash, an access token, a refresh token or the cookie value; no log line contains a username (R13; `docs/20` §7).
- **S29.** After S8–S11, the ledger contains exactly two `Identity.RefreshFamilyRevoked` rows (S10, S11) and none for S8 or S9.

### Provisioning and bootstrap

- **S30. Seeded grants.** On a fresh database, the migrations produce exactly eight `identity.Roles` rows (R19) and exactly these fourteen `identity.RolePermissions` rows, and a test compares them with `docs/10`: `stations.manage` × {`SystemAdministrator`, `RailwayAdministrator`}; `stations.read` × all eight roles; `users.read`, `users.manage`, `users.roles.manage`, `auth-sessions.revoke` × {`SystemAdministrator`}. Every seeded permission is a `Permissions` constant. No user is seeded.
- **S31.** Refresh tokens and passwords are stored only as hashes; a query over `identity` finds no raw token.
- **S32. Bootstrap.** On a database with no `SystemAdministrator`, the CLI creates exactly one user holding `SystemAdministrator`, marked must-change password, and writes one `Identity.UserCreated` audit row with null `ActorUserId` and `ActorRole`. A second run, when any `SystemAdministrator` exists, fails with a non-zero exit code, creates nothing and writes nothing. The generated or supplied initial password never appears in logs (R13).
- **S32a. Username rule.** Creating a user (API or CLI) with a username shorter than 3 or longer than 50 characters, or containing anything other than `a-z`, `0-9` and `.` (including upper-case letters), → `400`, nothing created. A duplicate username → `409 Identity.UserNameAlreadyExists`.

### Concurrency

- **S33.** Parallel rotations of the same token never produce two successors: exactly one `ReplacedByTokenId`, enforced in the database, not only in code. This is the storage half of S8.

## 6. API

Base path `/api/v1`, JSON camelCase, ProblemDetails with `errorCode` and `traceId` (`docs/20` §4). Error codes are `Auth.*` for sign-in/refresh/token errors and `Identity.*` for user administration (D14; `docs/20` §2), and **the prefix follows the path** (U1): endpoints under `/auth/*` return `Auth.*` codes, endpoints under `/users/*` return `Identity.*` codes. `/auth-sessions/*` and `/roles` are neither; they are user administration, so D14 gives them `Identity.*`. Request validation failures use the existing `400 Common.ValidationFailed`. Every authenticated endpoint below, except where stated, can also return `401 Auth.Unauthenticated` (no/invalid bearer token), `403 Auth.PasswordChangeRequired` (must-change password, R26 — every endpoint except `GET /auth/me`, `POST /auth/password`, `POST /auth/logout`, `POST /auth/refresh`) and `403` (missing permission).

### 6.1 Authentication (`/auth`)

| Method | Path | Request | Success | Error codes | Authorization | Cookie / Origin | Idempotency |
|---|---|---|---|---|---|---|---|
| POST | `/auth/login` | `{ username, password }` | `200 { accessToken, expiresAtUtc }` + refresh `Set-Cookie` | `400` validation · `401 Auth.InvalidCredentials` (uniform, R23) · `403 Auth.OriginRejected` · `429 Auth.TooManyRequests` | `.AllowAnonymous()`: caller has no token yet | **Sets cookie; Origin checked (R9)** | No |
| POST | `/auth/refresh` | none (cookie) | `200 { accessToken, expiresAtUtc }` + rotated cookie | `401 Auth.RefreshInvalid` · `409 Auth.RefreshSuperseded` (ADR-0016) · `403 Auth.OriginRejected` · `429 Auth.TooManyRequests` | `.AllowAnonymous()`: authenticated by the cookie, read inside the endpoint (R5) | **Cookie-bearing; Origin checked (R9)** | No. A benign duplicate is handled by R7, not `Idempotency-Key` (`docs/20` §5 does not list it) |
| POST | `/auth/logout` | none | `204` + `Set-Cookie` expiring the refresh cookie on `Path=/api/v1/auth/refresh` | `401 Auth.Unauthenticated` · `403 Auth.OriginRejected` | `.RequireAuthorization()` — self-service (D17); session from the token's `sid` (D12, C6) | **Sets (expires) cookie; Origin checked (R9)** | No; a second call on a revoked session gets `401` |
| GET | `/auth/me` | — | `200 { userId, userName, roles[], permissions[] }` | `401 Auth.Unauthenticated` | `.RequireAuthorization()` — self-service (D17) | — | n/a |
| POST | `/auth/password` | `{ currentPassword, newPassword }` | `204`; clears must-change (R26) | `400 Auth.PasswordRejected` (R18 policy) · `422 Auth.CurrentPasswordIncorrect` | `.RequireAuthorization()` — self-service (D17); allowed while must-change (R26) | — | No |

`/auth/me` returns the username only: the OQ34 ruling defines the staff identifier as the username, so F-002 stores no display name, employee number or Myanmar-script name. A client learns that the password must be changed from `403 Auth.PasswordChangeRequired` (R26); U2 adds no flag to the login or `/auth/me` response, so neither carries one.

### 6.2 Administration

Scope ruled by D9; permissions and grants by D8 (**provisional tech-lead ruling — not a Myanma Railways answer**). Lists are paginated (`docs/20` §4).

| Method | Path | Purpose | Permission | Notable errors |
|---|---|---|---|---|

| POST | `/users` | create account `{ userName, password, roles[] }` (R20 username rule; R18 password policy) | `users.manage` | `400` · `400 Identity.PasswordRejected` · `409 Identity.UserNameAlreadyExists` · unknown role `400`. The password is must-change (R26) |
| POST | `/users/{id}/disable` · `/users/{id}/enable` | disablement (revokes all sessions, R4) | `users.manage` | `404` · disable: `422 Identity.CannotDisableOwnAccount` (U5) · `422 Identity.LastAdministrator` (R27) |

| PUT | `/users/{id}/roles` | replace role assignments `{ roles[] }` | `users.roles.manage` | `422 Identity.CannotChangeOwnRoles` · `422 Identity.LastAdministrator` (R27) · `404` · unknown role `400` |
| POST | `/users/{id}/password-reset` | administrator reset `{ newPassword }` (revokes all sessions, R4); the new password is must-change (R26) | `users.manage` | `404` · `400 Identity.PasswordRejected` · `422 Identity.CannotResetOwnPassword` (U5) |

No endpoint edits role→permission grants. Grants change by reviewed migration (D8), because an API would let the holder of that permission grant anything to anyone. No endpoint returns a password hash, a token or a security stamp.

## 7. Data

Schema `identity` (`docs/07` §Module schemas; ADR-0012 `IIdentityDbContext`). ASP.NET Core Identity via `AddIdentityCore` (D1), its tables remapped into `identity` under these names. Which of Identity's optional tables (claims, logins, tokens) are mapped is a PLAN decision; F-002 uses none of them. All `*Utc` columns are `datetimeoffset(3)` with a UTC check constraint (`docs/20` §2, `docs/07` pattern). All ids are application-assigned GUIDs (ADR-0006).

**`identity.Users`**: `Id` PK · `UserName` `nvarchar(50)` with a check constraint for 3–50 characters of `a-z`, `0-9`, `.` (R20) · normalized user name, unique · `PasswordHash` · `SecurityStamp` · `IsDisabled`, `DisabledAtUtc` · `LockoutEndUtc`, `AccessFailedCount` (D3) · `PasswordChangedAtUtc` · `MustChangePassword` (set by the bootstrap and by every administrator-set password, cleared by own password change; D10, U2) · `CreatedAtUtc` · `rowversion` (concurrent admin edits vs login counters). **No TOTP columns** (D4b). No display name, employee number or Myanmar name (OQ34 ruling names only the username).

**`identity.Roles`**: `Id` PK · `Name` `nvarchar(50)` unique. **Seeded: the eight R19 identifiers** (provisional tech-lead ruling — not a Myanma Railways answer).

**`identity.UserRoles`**: `(UserId, RoleId)` PK, FKs. A user may hold several roles (D7).

**`identity.RolePermissions`**: `(RoleId, Permission nvarchar(100))` PK, FK to Roles. `Permission` follows `docs/20` §2 (`<resource>.<action>`), checked against `Permissions` constants by a test. **Seeded: the fourteen R11 rows (S30)** (provisional tech-lead ruling — not a Myanma Railways answer).

**`identity.AuthSessions`**: `Id` PK · `UserId` FK · `RevokedAtUtc` null (ADR-0016) · `CreatedAtUtc` · `ExpiresAtUtc` (created + 12 h, D12) · `RevocationReason` null (enum-as-string: `Logout`, `PasswordChanged`, `AdministratorPasswordReset`, `UserDisabled`, `AdministratorRevoked`, `FamilyReuse`) · index on `UserId`. One row per login; it **is** the refresh family (D12).

**`identity.RefreshTokens`** (C5, D12): `Id` PK · `SessionId` FK → AuthSessions · `TokenHash` `binary(32)` **unique** · `IssuedAtUtc` · `RotatedAtUtc` null · `ReplacedByTokenId` null, FK → RefreshTokens.Id, **filtered unique index where not null** (S33). A token's usable lifetime is its session's `ExpiresAtUtc` (no idle timeout, D12), so it carries no expiry column of its own.

**Database grants** (migration, `Security_AppDatabaseRole` pattern; ADR-0017 §3 spirit): `ycr_app` gets SELECT on all identity tables; **SELECT only on `Roles` and `RolePermissions`** (grants change by migration, D8); INSERT on `Users`, `AuthSessions`, `RefreshTokens`; INSERT and removal on `UserRoles` (role replacement — whether that is a `DELETE` grant or end-dated rows is PLAN); UPDATE only on the columns that legitimately change (`RevokedAtUtc`, `RevocationReason`, `RotatedAtUtc`, `ReplacedByTokenId`, password/lockout/disabled/security-stamp columns). **No DELETE on sessions or tokens (D18, PLAN).** A test asserts the grants, as F-001 S22 does.

**Not in F-002:** `IdempotencyRecords`; any TOTP or recovery-code storage (D4b).

Migrations are named `yyyyMMddHHmmss_Identity_<Change>` and reviewed per `docs/workflows/04-database-change.md`. The role and grant seed is in a migration, not in application code (D8).

## 8. Audit, logging, metrics

- **Audit** (ADR-0017, ADR-0021, ADR-0023): exactly the thirteen `Identity.*` actions in R22 — `LoginSucceeded`, `LoginFailed`, `LockedOut`, `LoggedOut`, `PasswordChanged`, `PasswordReset`, `UserCreated`, `UserDisabled`, `UserEnabled`, **`UserUnlocked`** (U3), `RolesChanged`, `SessionRevoked`, `RefreshFamilyRevoked` — one row per operation. `SubjectType` is the user (or the session for `SessionRevoked` and `RefreshFamilyRevoked` — PLAN fixes the subject constants). Snapshots may carry the resolved user's username, role list, disabled state and session id and reason; never passwords, hashes, security stamps, tokens or cookies (R13). A failed login with no resolved user: `SubjectId` null, and **no typed value** in any column. The bootstrap `UserCreated` has null `ActorUserId`/`ActorRole` (D10). Administration events carry the administrator as actor and the authorizing permission in `AuthorizedByPermission`. **Events with no bearer principal (U4, R12):** `LoginSucceeded` — actor the user who just signed in, with their roles; `LoginFailed` and `LockedOut` — actor null, subject the resolved user if any; `RefreshFamilyRevoked` — actor null (system action), subject the session's user. `ActorRole` is null whenever the actor is null. The within-grace predecessor is **not** audited (R7).
- **Logging** (`docs/20` §7): message templates; never log credentials, tokens, cookie values or usernames (D6 allows usernames in audit snapshots, not in logs).
- **Metrics** (`docs/17`): `AuthLoginSucceeded`, `AuthLoginFailed`, `AuthRefreshSuperseded` and `AuthRefreshFamilyRevoked` as log/metric event names (D6, C11), and **session/permission cache revocation latency** (`docs/17:35`), the measurable side of R3.
